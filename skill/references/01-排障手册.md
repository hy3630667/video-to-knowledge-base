# 排障手册

按「你看到的现象」索引。每条写清：现象 → 根因 → 解法。

---

## 1. 检索永远返回 0 条

**现象**：任何问题都查不到内容，但知识库里明明有文档。

**根因**：Ollama 没在跑。Dify 的向量检索靠它把文字转成向量，
**服务挂了会静默返回空，不报错** —— 这是它最难排查的地方。

**排查顺序**（按层次，别跳步）：

```
服务层 → 数据层 → 提示词层
```

1. **服务层**：
   ```powershell
   Invoke-RestMethod "http://127.0.0.1:11434/api/tags" -TimeoutSec 5
   ```
   没响应就启动：`Start-Process "D:\Ollama\ollama.exe" -ArgumentList "serve" -WindowStyle Hidden`
   起来后确认列表里有 `nomic-embed-text`。

2. **数据层**：查入库服务的 `/health`，看 `dify` 那项是否为 true。
   再看 Dify 控制台里文档的索引状态是不是 `completed`。

3. **提示词层**：以上都正常，才怀疑提示词。

**⭐ 别一上来就改提示词** —— 那是最后一步，不是第一步。

## 2. 入库服务提交了但一直没结果

**现象**：`/ingest` 返回了 job_id，但知识库里一直没出现新文档。

**根因**：两种可能 —— ① 服务中途挂了 ② 入库失败但你没查状态。

**解法**：

```powershell
Invoke-RestMethod "http://127.0.0.1:8090/jobs/<job_id>" -TimeoutSec 10
```

看 `status`：
- `failed` → 读 `error` 和 `logs` 最后几行
- `running` 卡在某个 `stage` 很久 → 看是不是转写大视频（11 分钟视频要 2.5–3.5 分钟）
- 查不到这个 job_id → 服务重启过，任务表丢了（`_ingest-jobs.json` 没落盘成功）

## 3. 服务起不来（端口被占）

**现象**：`入库服务.ps1 start` 报端口占用，或 health 一直没响应。

**排查**：

```powershell
Get-NetTCPConnection -LocalPort 8090 -State Listen
Get-Process -Id <上面的 PID>
```

**若占用者是旧的服务进程**：

```powershell
& "<你的工作目录>\入库服务.ps1" stop
& "<你的工作目录>\入库服务.ps1" start
```

**若占用者是别的程序**：改端口。启动时传参 `python ingest-service.py 8091`，
同时要改 Dify 里 HTTP 节点的 URL。

---

## 4. 改了脚本但行为没变

**现象**：改完 `ingest-service.py`，跑起来还是老逻辑。

**根因**：Python 服务启动后就把代码加载进内存了，**改文件不会自动重载**。

**解法**：

```powershell
& "<你的工作目录>\入库服务.ps1" restart
```

## 5. Dify 的 HTTP 节点报 SSRF 拦截

**现象**：
```
Access to 'http://host.docker.internal:8090/ingest' was blocked by SSRF protection
```

**根因**：Dify 有个 Squid 代理拦截所有出站请求，防止工作流被诱导访问内网。
默认白名单只有沙箱那一个 IP。

**解法**：

1. 查宿主机在容器里的 IPv4：
   ```powershell
   docker exec docker-api-1 getent ahosts host.docker.internal
   ```
   ⚠️ 会同时返回 IPv6 和 IPv4，**要用 IPv4 那个**（通常是 `192.168.65.254`）。

2. 改 `D:\Dify\dify-main\docker\.env`：
   ```ini
   SSRF_PROXY_ALLOW_PRIVATE_IPS=172.19.0.250/32,192.168.65.254/32
   ```

3. 重启两个容器：
   ```powershell
   cd D:\Dify\dify-main\docker
   docker compose up -d ssrf_proxy
   docker compose up -d api
   ```

**⭐ 测连通性要用对地址**：用网段网关（`172.19.0.1`）会超时，
容易误判成「容器连不到宿主机」。`host.docker.internal` 才是对的。

## 6. 下载失败

**现象**：`/jobs` 里 `status: failed`，`error` 提到下载相关。

**分平台看**：

| 平台 | 检查什么 |
|---|---|
| 抖音 / B站 | 抓取服务在不在：`Invoke-RestMethod "http://127.0.0.1:8080" -TimeoutSec 5` |
| 小红书 | XHS-Downloader 在不在（端口 5556）；cookie 文件是否过期 |
| 全部 | 链接是不是失效了、是不是私域内容（需登录的抓不到） |

**抓取服务重启**：
```powershell
docker restart dtk-v4
```

## 7. 转写出来全是错字

**现象**：入库成功，但文档质量差。

**根因**：三种可能 —— ① 视频音质差 ② 语速太快 ③ 专业词多

**解法**：本项目已经加了「大模型纠错」这一道，正常情况能修掉大部分。
如果还是差，看纠错工作流的输出，可能是：

- 纠错工作流挂了（`correct_transcript` 失败会回退成原始稿）
- 视频里专业词太多，超出了模型的知识范围

**⭐ 换更大的 whisper 模型通常没用** —— 实测 small 和 medium 各有各的错，
加纠错比换模型有效。

## 8. 新入库的视频查不到

**现象**：刚入库，问它的内容答不出来。

**根因**：**两个容易漏的步骤**：

1. **没打主题标签** —— 检索会按主题过滤，新文档没标签就被过滤掉
2. **主题判断的提示词没更新** —— 提示词里列的是旧视频的标题和关键词，
   新视频判不出主题

**解法**：

1. 打主题标签：见 `02-接口说明.md` 的「元数据绑定」
2. 更新主题判断提示词：
   ```powershell
   $node = "<你的 node 路径>"
   cd "<你的 dify-mcp 目录>"
   & $node "_fix-topic-prompt.mjs"
   ```
   这个脚本会从知识库读出真实内容，重新生成提示词并同步。

**⭐ 加新视频的完整流程是四步，不是一步：**
```
① 发链接入库
② 打主题标签
③ 更新主题判断提示词
④ 重新发布问答应用
```

**⭐ 每次加完都要回头核一遍**：跑步骤 ③ 时看它打印的「从知识库读出 N 个文档」，
**N 要等于知识库里实际的文档数**。不等就是漏了（见下一条）。

## 9. 同一主题有多个视频时，新视频没进主题判断提示词

**现象**：加了第二个属于同一主题的视频（比如 AI工具 底下已有 ComfyUI，再加一个 Agent 架构），
跑完步骤 ③，看输出发现**新视频不在列表里**，只有旧的那个。

**根因**：`_fix-topic-prompt.mjs` 原来用字典按主题归并，
**同一主题的第二个文档会覆盖第一个**。

```javascript
byTopic[topic] = { title, points }          // ❌ 覆盖
byTopic[topic] = [...]; byTopic[topic].push({...})   // ✅ 累积
```

**⭐ 这个 bug 只在「某主题出现第二个视频」时才暴露** ——
在此之前每个主题恰好一个视频，所以一直没撞出来。

**判别方法**：跑步骤 ③ 时看首行输出：

```
从知识库读出 5 个文档，分 4 类：      ← 5 要等于知识库实际文档数
  【AI工具】
    《Agent的7种架构…》              ← 两个都在才对
    《把 Agent 连上本地 ComfyUI！…》
```

**解法**：已修（改成数组累积）。若又出现，检查 `_fix-topic-prompt.mjs` 里
`byTopic` 是数组还是对象。

**⭐ 附带影响**：某主题视频变多后，该主题的检索召回条数会明显上升
（实测 AI工具 从 4 条涨到 9 条）。这是正常的，但如果太杂，
可以考虑把该主题再细分。

## 10. 同名链接重复提交会重跑

**现象**：同一个链接提交两次，等了两遍，以为第二次会跳过。

**根因**：幂等性靠的是**覆盖同名文档**，不是**跳过已存在**。
每次都会重新下载（若本地已有会跳过）、重新转写、重新纠错。

**解法**：**提交前先查一下 `/jobs`**，看看这个 URL 最近处理过没有：

```powershell
Invoke-RestMethod "http://127.0.0.1:8090/jobs" -TimeoutSec 10 |
  Select-Object -ExpandProperty jobs |
  Where-Object { $_.url -eq "<要提交的链接>" } |
  Select-Object -First 1 job_id, status, created_at
```

**⭐ 已知重复记录**：`https://v.douyin.com/FeatxeTTPMQ/`（电商详情页那个）
在历史里出现过 3 次，都是因为我没先查就重复提交。

## 11. Dify 整个打不开

**现象**：浏览器打开 `http://localhost` 没反应。

**排查**：

```powershell
# Docker 在不在
docker info

# 容器状态
cd D:\Dify\dify-main\docker
docker compose ps
```

**Docker 没起来**：
```powershell
Start-Process "D:\Docker\Docker Desktop\Docker Desktop.exe"
```
等 30–60 秒它才会就绪。

**容器没起来**：`docker compose up -d`

**⭐ 一键全起**（推荐）：
```powershell
& "<你的工作目录>\启动全部服务.ps1"
```
它会按顺序等 Docker、Ollama、Dify，最后起入库服务。

## 12. 重启电脑后全都不见了

**现象**：重启后什么都用不了。

**根因**：三个服务都要自启，少配一个就断。

**解法**：确认这三项都在：

| 服务 | 自启方式 |
|---|---|
| Docker Desktop | 设置里勾「Start Docker Desktop when you sign in」 |
| Ollama | 启动文件夹里的 `Ollama.lnk` |
| 入库服务 | 启动文件夹里的 `视频知识库-启动服务.lnk` → `启动全部服务.ps1 -Quiet` |

**启动文件夹**：`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`

**⭐ 手动全起一次**：`& "<你的工作目录>\启动全部服务.ps1"`

## 附：服务清单

| 服务 | 端口 | 在哪 | 挂了会怎样 |
|---|---|---|---|
| Dify（17 容器）| 80 | Docker | 全部功能不可用 |
| Ollama | 11434 | **宿主机进程** | 检索静默返回 0 条 |
| 入库服务 | 8090 | **宿主机进程** | 提交链接报连接错误 |
| 抓取服务 | 8080 | Docker | 下载失败 |
| XHS-Downloader | 5556 | 需要时手动 | 小红书链接下载失败 |

**⭐ 加粗的两个不在 Docker 里，Docker 重启不会带起它们。**
