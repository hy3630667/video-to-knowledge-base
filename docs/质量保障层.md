# 质量保障层

> 目标架构图里画的是**运行时**（数据怎么流）。这一层画的是**怎么知道它坏了**。
> 本文所有数字都来自实测，不是设计目标。
> 最后更新：2026-10-08

---

## 一、为什么需要这一层

**起点是一个静默失败**：一个 64 分钟的视频入库后，知识库里**只有 105 个字**，
而整条流程从头到尾打印的是「✅ 完成」。

**根因（硬证据）**：纠错 LLM 的输出 `finish_reason = "length"` —— 被 `max_tokens` 截断了。
截断的位置恰好让 `## 知识点` / `## 问答对` 两节没生成，
而合规策略正确地丢弃了 `## 校对稿` → **主体内容全部丢失，且没有任何一处报错**。

> **一个能报「完成」的坏产出，比一个报错的失败危险得多。**
> 前者会静默污染知识库，后者至少会被人发现。

由此确立了本层的两条原则：

| 原则 | 含义 |
|---|---|
| **闸门要「真检查」** | 不能只查「有没有这个标题」，要查「标题下面有没有实际内容」 |
| **不确定就别入库** | 闸门不过 → **拒绝入库**，而不是「退而求其次写个半成品」 |

## 二、五道闸门

### 闸门 1｜规则清洗（确定性，无 LLM）

**做什么**：去掉 ASR 转写稿里的句首口头语（「嗯」「那个」「就是说」）。

**关键取舍**：**只删句首，句中的保留**。
「那个东西」在句中往往是有效指代，删了会改语义；而句首的「那个」几乎总是填充词。

**为什么放第一道**：它零成本、零风险、完全可预测，能减少后面 LLM 的输入噪音。

### 闸门 2｜分块 map-reduce 纠错（治截断）

**问题**：一次性把 2 万字喂给纠错 LLM → 必然撞 `max_tokens` 截断 → 就是那个 105 字事故。

**做法**（分块阈值 **3500 字**，在**句子边界**切，保证不切断句子）：

```
原文 22314 字
  → 规则清洗
  → 切成 7 块（每块 ≤3500 字，句子边界对齐）
  → 逐块送纠错（MAP）
  → 合并 + 跨块去重（REDUCE）
  → 合并后 9178 字 / 12 段
```

**不丢字校验**：`''.join(分块) == 清洗后原文` —— 切分本身必须无损。

**同时**：纠错节点显式设 `max_tokens = 8000`。
开源依据（拾语 `backend/cleaner.py`）的注释直接写着：
> DeepSeek V4 默认思考模式会吃满 max_tokens，结构化 JSON 场景要显式关掉。

我们对应地把纠错节点的 `thinking` 设为 `false`。

### 闸门 3｜校验闸门（真检查，不是存在性检查）

纠错产出的**每一块**都必须满足：

| 检查项 | 类型 |
|---|---|
| 有 `## 知识点` 且**下面有实际条目** | **真检查** |
| 有 `## 问答对` 且**下面有实际 Q/A** | **真检查** |
| 整体至少有一个合规分节 | 结构检查 |

**「真检查」与「存在性检查」的差别是本层的核心**：

| | 存在性检查（错） | 真检查（对） |
|---|---|---|
| 判据 | 文本里有 `## 知识点` 这几个字 | 该标题下**至少有 N 条实质条目** |
| 截断的输出 | ✅ 误判为通过 | ❌ 正确拦下 |

> 这个区分来自开源项目 `learning-video-skills` 的原文：
> 「校验器**双向有分辨力**（未填充模板 11 错+1 提醒 / 合格笔记 0 错 0 提醒）」
> 「`validate.py` 满分 ≠ 手册可用 —— 它查结构，查不出你有没有读对画面」

**闸门不过的后果**：**这一段落不入库**（旧行为是「纠错失败就用原始转写稿」，那会把错字和后处理噪音一起灌进库）。

### 闸门 4｜专名漂移检查（治 LLM 改写专名）

**真实事故**：转写稿里正确的 `Reason加Act`，被 LLM「纠错」改成 `Reason加Actor`，然后写进了知识库。

**做法**：
1. 从**原始转写稿**抽候选专名（ASCII/技术词，去虚词）
2. 纠错后逐个核对：原稿有的专名，纠错稿里**还在不在**（按**词边界**匹配，不是子串）
3. 不在了 → 用相似度找「疑似的改写结果」，报出来

```
专名漂移告警（原稿有、纠错稿里没了）：
  · Act → 疑似被改成 Actor（相似度 0.75）
  ⚠️ 专名不信任 LLM 纠错：请对照视频画面文字（OCR）核对
```

**实现踩过的两个坑**（都已修）：
- **子串匹配太松**：`Act` 是 `Actor` 的子串 → 事故**漏报**。必须加字母/数字词边界
- **猜测误报**：`ReAct` 和 `Actor` 与 `Act` 的相似度都是 0.75，不筛「原稿里没有的新词」就会误报成 `Act → ReAct`

**⚠️ 诚实说明**：这是**降级方案**。开源依据（`learning-video-skills`）的理想解是
「**专有名词以 OCR 为准** —— 声学模型解决不了同音词（「短距」/「短剧」），画面文字才是可靠来源」。
本机没接 OCR，所以做的是**把静默改写变成可见告警**，不是根治。

### 闸门 5｜内容去重（按内容分，不按链接分）

**真实场景**：一个 19 分P 的课程里，**P2 和 P3 是同一节课的重复投稿**。

**判定证据**（不是靠标题相似猜的）：

| 对比项 | P2 | P3 |
|---|---|---|
| 全量音频 MD5 | `D6CB799B29CE…` | **完全相同** |
| 精确时长 | 362.927891 秒 | 362.927891 秒 |
| 原始转写稿 | 1409 字 | 1409 字（逐字相同）|
| 视频文件 | 8.9 MB | 9.2 MB（**重编码过，所以不同**）|

→ 音频逐字节相同 = **同一份录音**。视频文件不同只因为重新编码。

**做法**：下载后先算**音频前 120 秒的 md5**，命中台账就跳过（连转写都不做）。

**为什么用音频指纹而不是标题**：标题可能被改、可能被截断（实测同一课程里 P2/P3 标题一模一样，但也有分P 标题重名却内容不同的情况）。
**内容指纹是不会骗人的。**

**分辨力验证**（防「把不同课当重复丢掉」）：
- 同一文件两次 → 指纹必须相同
- **不同音频 → 指纹必须不同**（这条比上一条更重要）
- 台账损坏 → 不崩，只是查不到
- 算不出指纹 → 不判为重复

## 三、评测体系（没有它就没有「改好还是改坏」的判据）

### 三层测试，各有分工

| 层 | 规模 | 测什么 | 什么时候跑 |
|---|---|---|---|
| **用例测试** | **67 项** | 代码逻辑（切块/去重/闸门/专名/评测器本身） | 每次改代码 |
| **端到端评测集** | **36 题**（29 题带期望视频） | 答案对不对 **+ 检索对不对** | 每次改提示词/库结构 |
| **主题路由测试集** | **36 题** | 只测「该判到哪个主题」 | 每次改主题提示词 |

### 端到端评测集的两个关键字段

```json
{ "id": "E10", "kind": "事实",
  "q": "配音的第一步做什么？",
  "expect": ["预训练音色", "旁白"],     ← 答案里必须出现的要点
  "forbid": ["来源："],                 ← 不许出现的词
  "expect_doc": "配音与对口型" }        ← ⭐ 这段内容该来自哪个视频
```

`expect_doc` 是**检索层指标**的来源：

| 指标 | 含义 |
|---|---|
| **P@1** | 期望视频排在检索结果第 1 名的比例 |
| **MRR** | 平均倒数排名（排第 2 得 0.5，排第 4 得 0.25）|
| **噪音占比** | 检索结果里非期望视频的片段占比 |
| **元数据段数** | 有没有元数据段在抢检索槽位 |

### ⭐ 打分器本身也要有「双向分辨力」

**为什么**：如果评测**全过**，它证明不了自己**能发现问题** —— 万一打分器写松了，将来真出回归它也会报「通过」。

参考 `learning-video-skills` 的闸门验证法（喂坏产出必须报错 + 喂好产出必须不报），
我们给打分器写了 **18 项自检**，两头都测：

- **8 个坏产出必须被判不过**：缺要点、只命中一半、含禁用词、含错误专名 `Actor`、
  该拒答却答了、直答题却拒答、越界题没声明、意图不符
- **6 个好产出必须被判通过**：全要点、英文变体（`多Agent|Multi-Agent`）、拒答标记、直答、多种越界措辞

### 实测：补题的代价与价值

题库从 22 题（只覆盖原 8 篇）补到 36 题（覆盖全部 14 篇）后，指标**大幅下降**：

| 指标 | 22 题时 | 36 题时 |
|---|---|---|
| 计分题通过 | 20/20 (100%) | **29/34 (85.3%)** |
| P@1 | 15/15 (100%) | **25/29 (86%)** |
| MRR | 1.000 | **0.897** |
| 噪音占比 | 41% | **57%** |

**这不是系统变差了，是终于测出来了。** 补题立刻暴露三类真问题：

| 类别 | 实例 | 根因 |
|---|---|---|
| 主题误判 | 「反推出来的绘图提示词要怎么精简？」→ 判成 AI应用 | 路由 → 检索错主题 → 拒答 |
| 检索召回 | 「配音的第一步做什么？」→ 10 条里没有「配音与对口型」 | 合并文档的分段内容被稀释 |
| 答案不完整 | 「剧本完成后还能生成什么？」→ 只答了分镜，漏了人物/场景/道具 | 生成层遗漏 |

> **不做这 14 道题，就永远不知道合并方案有没有把检索搞坏** —— 只能靠偶然撞见。

## 四、贯穿全层的一条设计教训

### 库变大以后才显形的问题：提示词膨胀 → 分类退化

**因果链**（有对照实验）：

| | 库 8 篇 | 库 26 篇 |
|---|---|---|
| 主题判断提示词 | 2079 字（**塞了全库标题+知识点**）| **6335 字** |
| 「调色台的操作流程」判到 | `AI视频` ✅ | **`AI工具`** ❌ |
| 结果 | MiniMax 排第 1，正常回答 | 主题过滤挡掉 MiniMax → **拒答** |

**修法**：提示词改成**紧凑版** —— 每类只留有限个高辨识度关键词（**大小与库规模脱钩**），
再加显式消歧规则。

**结果**：6335 字 → **744 字**（−88%，每问省约 2800 token），主题判断恢复正确。
后续补了消歧词后为 913 字，路由测试 **36/36**。

> **教训**：把一个会随数据规模增长的东西（全库内容）塞进提示词，
> **它短期能跑、长期必坏**。提示词的复杂度应该与业务复杂度挂钩，**不该与数据量挂钩**。

## 五、设计来源（面试可讲出处）

| 机制 | 来源 | 抄了什么 |
|---|---|---|
| 分块 3500 字 + 句子边界切 | 拾语 `backend/cleaner.py` | 阈值（3500）与「句子边界优先」 |
| `max_tokens` 显式设 8000 | 拾语 `cleaner.py` 注释 | 「思考模式会吃满 max_tokens，结构化场景显式关掉」|
| 闸门「真检查非存在性检查」 | `learning-video-skills` | 判据从「有没有这个标题」改成「标题下有没有实质条目」|
| 打分器双向分辨力 | `learning-video-skills` | 「喂坏产出必须报错 + 喂好产出必须不报」|
| 专名以 OCR 为准 | `learning-video-skills` | 理想解引用；本机无 OCR，做降级版漂移检查 |
| 多分P 批量处理 | 拾语 | 「多分P系列一键排队批量总结并合并合集笔记」|

## 七、❓ 已知局限（诚实说明）

1. **专名检查没有 OCR** —— 画面文字才是同音词（短距/短剧）的可靠来源，本机未接
2. **没有真 rerank 模型** —— 用 `weighted_score` 算法加权替代（Ollama 全版本无 `/api/rerank`）；
   当前噪音 57%、P@1 86%，**rerank 是能直接改善这两项的手段**
3. **主题消歧规则是手写的** —— 有过度拟合风险，靠 36 题路由测试集约束
4. **合并主题文档可能降低具体问题的召回** —— 见上文「检索召回」实例，尚未做
   「一课一篇 vs 合并」的 A/B 验证
5. **元数据段已清零**，但新入库流程仍依赖「事后绑主题」这一步，忘了绑就会漏
