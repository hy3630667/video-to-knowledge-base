# 视频知识库 Agent —— 完整技术文档

> 建立：2026-10-05
> 目标：把一个抖音/B站/小红书视频链接，自动变成可检索、可问答的知识库
> 实测总耗时：**14.6 秒**（27 秒视频，全链路）
> 成本：**0 元**（全自托管，无 API 费用）

---

## 一、这条链路解决什么问题

**输入**：一个视频链接（别人的视频）
**输出**：进入 Dify 知识库的结构化文档，可用自然语言问答

**和 A0–A8 的区别**（重要，别混）：

| | A0–A8 体系 | 本条链路 |
|---|---|---|
| 方向 | **生产**：自有品牌 → 产出短视频 | **理解**：别人的视频 → 提取知识 |
| 输入 | 自己的品牌资料、素材 | **别人的**视频链接 |
| 输出 | 分镜表、口播文案、标题 | 知识库 + 可问答 |
| 唯一交集 | 「素材库」可作 A3-对标侦察的样本源 | 本条链路是它的**上游供应商** |

## 二、架构总览

```
视频链接（抖音/B站/小红书）
    │
    ├─ ① 抓取 ────────────────────────────────────────
    │    抖音/TikTok → Douyin_TikTok_Download_API (Docker, :8080)
    │    B站        → 同一个服务（专门端点，bv_id + cid）
    │    小红书      → XHS-Downloader (REST API, :5556)
    │    兜底        → yt-dlp（YouTube/B站字幕直取）
    │
    ├─ ② 转写 ────────────────────────────────────────
    │    ffmpeg 抽 16kHz 单声道 WAV
    │    → faster-whisper（CPU int8，6.73x 实时）
    │    → opencc 繁转简
    │
    ├─ ③ 纠错 + 知识点提取 ───────────────────────────
    │    Dify 工作流「转写稿纠错与知识点提取」
    │    开始 → LLM(thinking:false) → Code(剥思维链) → 结束
    │
    ├─ ④ 写入知识库 ──────────────────────────────────
    │    dify-mcp: file.upload → knowledge.create_document
    │
    └─ ⑤ 问答 ────────────────────────────────────────
         Dify chatflow「视频知识库问答」
         开始 → 知识检索 → LLM → 直接回复
```

### ① 抓取：抖音

| 项 | 值 |
|---|---|
| 工具 | `evil0ctal/douyin_tiktok_download_api:V4.1.2` |
| 部署 | 单容器，`-p 8080:80`，420 MB 镜像 |
| 依赖 | **无**（不需要数据库/Redis/密钥）|
| 实测耗时 | **1.0 秒**（2.56 MB 视频）|
| Cookie | **镜像自带的 2025-03 那份仍可用，不用自己抠** |

**关键端点：**

| 端点 | 参数 | 用途 |
|---|---|---|
| `/api/hybrid/video_data` | `url`（必填）, `minimal` | 拿元数据 + 视频直链（**只支持抖音/TikTok**）|
| `/api/download` | `url`, `prefix`, `with_watermark` | 直接下载视频文件 |
| `/api/douyin/web/get_aweme_id` | `url` | 分享短链 → aweme_id |
| `/api/bilibili/web/fetch_one_video` | `bv_id` | B站视频信息 |
| `/api/bilibili/web/fetch_video_playurl` | `bv_id` + `cid` | B站 dash 直链 |

**⚠️ 坑 1：`hybrid/video_data` 不支持 B站。**
README 里 `hybrid_parsing` 的 docstring 写「Douyin/TikTok URL」，但示例提示语又写「Douyin/TikTok/Bilibili」—— 实测**只有抖音/TikTok 能过**，B站必须走 `/api/bilibili/*` 专门端点。

**⚠️ 坑 2：B站的参数名是 `bv_id` + `cid`，不是 `bvid`。**
用 `bvid=` 会得到 `422 Unprocessable Entity`。

**⚠️ 坑 3：`minimal=true` 会剥掉 `duration` 字段。**
要拿完整元数据必须用 `minimal=false`。

**⚠️ 坑 4：v5 是过度工程。**
`latest` 标签（v5）的 compose 栈是 **6 个容器**（api + worker + postgres + redis + 2 sidecars），需要 `DTK_SECRET_KEY`（≥32 字符）、`POSTGRES_PASSWORD`、`REDIS_PASSWORD`，还要跑 `migrate`。**v4 才是对的量级**：单容器、无数据库、无密钥。

### ③ 纠错：Dify 工作流

**⚠️ 坑 8（最大的坑）：DeepSeek 推理模型的 `<think>` 输出会污染结果。**

`deepseek-flash` 是推理模型，输出长这样：
```
<think>
<!--dify-deepseek-reasoning-->我们需要根据用户提供的主题创作标题...
（几百字推理过程，包括字数核算）
</think>
（真正的答案）
```

**在 Dify 工作流里，这个推理过程会**原样进入下游节点的值**，被代码节点当成内容拆进数组。**

**根因**（在 DeepSeek 插件源码里找到）：
```python
# langgenius/deepseek-0.0.24/models/llm/llm.py
class DeepseekLargeLanguageModel(OAICompatLargeLanguageModel):
    _THINK_MARKER = "<!--dify-deepseek-reasoning-->"
    _THINK_PATTERN = re.compile(rf"<think>\n{re.escape(_THINK_MARKER)}(.*?)\n</think>", re.DOTALL)
    _THINKING_MODELS = ("deepseek-flash", "deepseek-v4-flash", ...)
```

**解法：三重防御**

| 层 | 做法 |
|---|---|
| **① 源头** | LLM 节点 `completion_params` 加 **`thinking: false`** |
| **② 引导** | 提示词写「输出纪律」段：禁止输出思考过程 |
| **③ 兜底** | 代码节点「剥离思维链 + 规范化」（抄自 A0）|

**兜底代码（复用 A0 的实现）：**
```python
import re

def main(raw: str) -> dict:
    text = raw or ""
    original_len = len(text)

    text = re.sub(r"(?s)<think>.*?</think>", "", text)          # 剥 think 块
    text = re.sub(r"(?s)<!--.*?-->", "", text)                  # 剥 HTML 注释
    text = re.sub(r"(?s)^\s*```[a-zA-Z0-9_-]*\s*\n", "", text)  # 剥开头代码围栏
    text = re.sub(r"(?s)\n```\s*$", "", text)                   # 剥结尾代码围栏

    m = re.search(r"(?m)^#{2}\s", text)
    if m:
        text = text[m.start():]                                 # 从第一个 ## 开始

    text = text.strip()
    text = re.sub(r"\n{3,}", "\n\n", text)
    text = re.sub(r"[ \t]+\n", "\n", text)

    return {"clean": text, "clean_len": len(text),
            "removed_chars": original_len - len(text),
            "has_think": 1 if "<think>" in (raw or "") else 0}
```

**效果对比：**

| 问题 | 修复前 | 修复后 |
|---|---|---|
| 输出结构 | `<think>` + 推理 + 答案混在一起 | ✅ 直接 `## 校对稿` |
| 工作**榴** | ❌ 没改 | ✅ **工作流** |
| 详情**业** | ❌ 没改 | ✅ **详情页** |
| **时操** | ❌ 没改 | ✅ **实操** |
| 标点 | 无 | ✅ 句号、顿号都补上 |
| `reasoning_content` | 有内容 | ✅ 空字符串 |

**实测：`completion_tokens: 235, latency: 1.431s`**

### ⑤ 问答：RAG chatflow

**chatflow 结构：**
```
开始(用户问题) → 知识检索 → LLM(基于片段回答) → 直接回复
```

**⚠️ 坑 11：chatflow 的 `run-draft` 要**两个**参数。**

```bash
# 错：只传 inputs
--inputs '{"query":"..."}'     # → "query is required"
# 错：只传 query
--query "..."                  # → "argument 'inputs' must be an object"
# 错：传空 inputs + query
--inputs '{}' --query "..."    # → "query is required in input form"
# ✅ 对：两个都传
--inputs '{"query":"..."}' --query "..."
```

**根因**（`api/core/app/apps/base_app_generator.py` 行 213）：
```python
if value is None:
    if variable_entity.required:
        raise ValueError(f"{variable_entity.variable} is required in input form")
```
**start 节点的必填变量从 `inputs` 取；chat 层的问题是独立参数。**

**⚠️ 坑 12：检索分数在 `metadata.score`，不在顶层。**

```json
{
  "content": "...",
  "title": "...",
  "metadata": {
    "score": 0.6296574,          ← ⭐ 分数在这里
    "segment_hit_count": 7,
    "dataset_name": "测试-视频知识库"
  }
}
```
**读顶层 `score` 会得到 `undefined` → 显示 0.000，看起来像「检索坏了」，其实是显示 bug。**

**实测检索分数：0.63 / 0.62 / …（与 `hit_testing` 的 0.65 一致）**

**⚠️ 坑 13：提示词要明确要求「不知道就说不知道」。**

**修前**：问「视频里提到用什么工具了？」→ 复述主题/人群/教学方式（答非所问）
**修后**：→ **「知识库里没有关于『工作流具体怎么搭建』的内容。」**

关键提示词改动：
```
1. **先判断检索片段能否回答问题。**
   - 不能回答 → 第一句就写「知识库里没有关于『XXX』的内容」，然后停止，不要硬凑。
   - 部分能回答 → 先答能答的，再明确说「关于 XXX 部分，知识库里没有提及」。
C. **不要复述输入。** 用户问什么就答什么，不要把所有检索到的内容都罗列一遍。
```

**⚠️ 坑 14（最隐蔽的一个）：LLM 节点提示词里**忘了注入用户问题**。**

**症状**：4 个问题里 3 个答非所问，而且**每个回答的主题都不一样**，像是随机挑的：
```
问「安装需要什么条件？」      → 答「电商详情页工作流搭建」（另一个文档）
问「支持哪些 Agent 客户端？」 → 答「是否收费」
问「Comfy MCP 能做什么？」    → 答「是否收费」
```
**但检索明明命中了完美片段**（0.756「支持将 Claude、Codex…」、0.720「用自然语言可以对 ComfyUI 做什么？→ 构建、编辑和运行工作流」）。

**根因**：chatflow 的 LLM 提示词模板里**只有检索结果，没有用户问题**：
```
=== 输出纪律 ===
=== 回答规则 ===
=== 检索到的片段 ===
{{#knowledge_retrieval.result#}}      ← 只有片段！
```
**→ LLM 根本不知道用户在问什么，只能从片段里随便挑一个主题来回答。**

**⭐ 为什么初版「看起来能答对」**：提示词的措辞（「准确回答用户关于『视频里怎么讲的』的问题」+「必须标注来源」）让它倾向于**总结片段内容**。这个行为恰好和「这个视频讲的是什么」类问题吻合，所以前几轮测试全过了。**一问「安装需要什么条件」这种具体问题，立刻暴露。**

**修法（一行）**：
```
=== 用户的原始问题 ===
{{#start_1.query#}}

=== 检索到的片段 ===
{{#knowledge_retrieval.result#}}
```

**⭐⭐ 对比验证（同一个知识库、同一批问题）：**

| 问 | 修前 | 修后 |
|---|---|---|
| 安装需要什么条件？ | ❌ 答「电商详情页工作流搭建」 | ✅ 独显电脑 / ComfyUI / MCP 客户端 |
| 支持哪些 Agent 客户端？ | ❌ 答「是否收费」 | ✅ Claude、Codex、Cursor + 来源 |
| 适合哪些场景？ | ❌ 答「哪些人适合学工作流」 | ✅ 两条视频用途 + 排除无关片段 |
| Comfy MCP 能做什么？ | ❌ 答「是否收费」 | ✅ 6 条要点 + 来源 + 场景 |

**⭐⭐⭐ 教训：RAG 提示词里「检索结果」和「用户问题」缺一不可。只给检索结果，模型会退化成「片段摘要器」。**

**⚠️ 坑 15：提示词里给**过于具体的例子**会污染行为。**

**症状**：为了治「过度拒答」，我在判定规则里加了两个具体例子：
```
例：用户问「安装需要什么条件」，片段里有「一台带有独立显卡的电脑…」→ 这就是答案，必须回答
例：用户问「支持哪些客户端」，片段里有「Claude、Codex 或 Cursor」→ 这就是答案，必须回答
```
**结果：模型把这两个例子当成了**回答模板**，所有问题都往「安装条件」上套。**

**⭐ 修法**：把具体例子换成抽象标准，并单独加一条纪律：
```
1. **正面回应用户问的那件事。** 用户问 A，就答 A。
   - 不要答成 B（哪怕 B 也在片段里、哪怕 B 更完整）。
   - 不要用「某个相关话题的条件/方法/场景」去替代用户真正问的东西。
   - 如果片段里 A 的信息少而 B 的信息多，仍然只答 A，可以简短。
```

**⭐⭐ 教训：提示词里的「示例」会被模型当成「输出格式」。要举例就举**结构性**的，不要举**内容性**的。**

**⚠️ 坑 16：向量检索的「万能磁铁」—— 片尾客套话会霸占 top_k。**

**症状**（11.6 分钟长视频入库后）：

```
查「这个视频讲了什么」→ 0.708  「好，这就是本次的分享。有任何的意见或者是建议
                              以及有好的想法都可以加我进群进行反馈，希望大家能给
                              一个一键三连，点赞加关注。」
```
**⭐ 而且**三个不同视频**、**所有查询**下，这同一个片段都排第一。**

**根因**：该片段仅 71 字，却密集包含「分享/意见/建议/想法/反馈/关注/点赞」等**高频通用词** → 与任何中文问题的余弦相似度都偏高 → 成为「万能磁铁」。

**修法**：在纠错工作流的提示词里，把「删客套话」提到**约束优先级第 1 位**：
```
1. **删客套话（必须做）**。片头问候和片尾套话一律删除，例如：
   - 片头：「大家好我是XX」「你怎么才来」「点赞关注不迷路」
   - 片尾：「这就是本次分享」「有任何意见建议可以加群反馈」「求一键三连」「谢谢大家拜拜」
   只保留**正片内容**（讲解、演示、结论）。
```

**效果：6/6 全删，磁铁消失。**

**⭐ 但随即出现「第二代磁铁」**：
```
新磁铁 = 「怎么生成最终的调好的视频？点击写入参数，点击完成之后可以使用小眼睛功能…」
```
**它在 3 个视频的所有查询里都排前二，甚至在全不相干的查询（「电商详情页生成工作流」）下拿到 0.786 排第一。**

**根因**：这个片段**设问句多**（「怎么XX？」），而用户查询也是问句 —— **问句↔问句的向量天然接近**。

**⭐⭐⭐ 结论：向量检索对「问句型内容」有系统性偏好。去掉了客套话，还会冒出设问句。这是模型层面的问题，靠清洁数据只能缓解、不能根治。**

**⚠️ 坑 17（订正版）：混合检索的开关在**知识库级**，不在工作流节点级。**

> **订正说明**：我最初判断「工作流节点不支持混合检索」是**错的**。排查了三层才找到真凶。

**症状**：把节点的 `top_k` 从 5 改到 10、加 `score_threshold`、改 `weights`，检索结果**完全没变**（分数一模一样）。

**三层排查过程：**

| 层 | 我的假设 | 实际情况 |
|---|---|---|
| ① 字段存在性 | `weights` 不在 `MultipleRetrievalConfig` 里 | ❌ **错了** —— `entities.py` 行 23 明确有 `weights: WeightedScoreConfig \| None = None` |

## ⭐ 方案 A 已实施（自定义分段 + 标题前缀），效果显著

**技术实现**（`ProcessRule` 支持自定义分段，见 `processing_entities.py`）：
```python
class Segmentation(BaseModel):
    separator: str = "\n"       # 自定义分隔符
    max_tokens: int
    chunk_overlap: int = 0

class Rule(BaseModel):
    pre_processing_rules: list[PreProcessingRule] | None = None
    segmentation: Segmentation | None = None
    parent_mode: Literal["full-doc", "paragraph"] | None = None
```

**⚠️ 关键：`create_document` 的 `--file-ids` 快捷方式会强制 `process_rule.mode="automatic"`，拿不到自定义分隔符。**
**→ 必须用完整 `body` 形式（`buildKnowledgeDocumentBody` 检测到 body 是对象就原样透传）：**
```json
{
  "name": "文档名",
  "indexing_technique": "high_quality",
  "data_source": { "info_list": { "data_source_type": "upload_file",
                                  "file_info_list": { "file_ids": ["xxx"] } } },
  "process_rule": {
    "mode": "custom",
    "rules": {
      "pre_processing_rules": [
        { "id": "remove_extra_spaces", "enabled": true },
        { "id": "remove_urls_emails", "enabled": false }
      ],
      "segmentation": { "separator": "\n\n===\n\n", "max_tokens": 1400, "chunk_overlap": 0 },
      "parent_mode": "paragraph"
    }
  }
}
```

**⭐ pipeline 里的实现（`build_chunks`）**：
1. 按 `##` 分节（校对稿 / 知识点 / 问答对）
2. 每节超过 900 字就按段落再聚合，保证单块 ≤900 字
3. **每块都以 `【视频标题】` 开头**
4. 用 `\n\n===\n\n` 连接后上传

1. **分数提升** —— Comfy MCP 那条从 0.692 → **0.830**
2. **完全不串台** —— 每个查询前 3 名都是同一正确视频
3. **来源标注更规范** —— LLM 能从片段前缀直接读到视频标题（带《》和 BV 号）
4. **意外好处** —— 第 7 问模型主动发现「知识库里只有一个 B站 视频，另一个是抖音」，这是**正确的自我纠错**

**⚠️ 坑 18：写入原始转写稿会污染检索。**

**症状**：长视频文档 7452 字 / 18 段，其中**第 13-18 段是 ASR 未纠错的原始稿**（带「接放重影」「体式词」等错字）。

**根因**：pipeline 的 `write_to_dify` 把「纠错稿」和「原始转写稿」**都写进了同一个文档**，原始稿被切成额外 6 段参与检索。

**修法**：知识库只放纠错稿，原始稿留在本地 mp4 旁边。
```python
log("  使用纠错稿作为唯一内容（不写原始稿，避免错字段落污染检索）")
body = f"# {title}\n\n平台: {platform}\n...\n---\n\n{corrected}\n"
```

**效果**：长视频文档从 7452 字降到 4042 字，段数从 18 降到 12。

# 九、Agentic RAG 升级（2026-10-07）

## 9.1 为什么要改

原来的问答链路是标准 RAG 的直线：`检索 → 回答`。实测暴露三个问题：

| 问题 | 现象 |
|---|---|
| 指代不明 | 问「**那个**视频里说的两步」，模型不知道「那个」指谁，直接拒答 |
| 聚合统计 | 问「知识库里有几个视频」，答「2 个」（实际 4 个）|
| 无检索质量判断 | 检索回来 10 条，不管好坏直接喂给模型 |

缺的是「**评估**」和「**重试**」两个环节。

# 十、这次升级踩的三个新坑

## 坑 19：检索返回 0 条，先查 embedding 服务是否活着

**现象**：改造后第一版，所有问题都答「知识库里没有」，检索 0 条。

**排查三层：**

| 层 | 怀疑 | 结果 |
|---|---|---|
| ① | 改写输出是关键词堆（`书籍转技能 Skill 功能 用途…`），稀释了向量 | 改成自然句 → **仍是 0 条** |
| ② | `score_threshold: 0.3` 卡太严 | 关掉 → **仍是 0 条** |
| ③ | **Ollama 挂了** | 🎯 **真凶** |

**根因**：Ollama 是宿主机上的独立进程（`127.0.0.1:11434`），不在 Docker 里。
Docker Desktop 重启会把 16 个容器拉起来，但**不会带起 Ollama**。
而 Dify 的向量检索拿不到查询向量时不会报错，**只是返回空列表**，
看起来像提示词问题。

**判据**：检索 0 条 → 先 `curl 127.0.0.1:11434/api/tags`，再调查询和阈值。

## 坑 20：Dify 的记忆是节点的 `memory` 字段，不是 `context`

**我一开始改错了地方** —— 以为 LLM 节点的 `context.enabled = true` 就是开历史对话。
改完没有任何效果。

**读了源码才发现**（`api/core/workflow/system_variables.py`）：

```python
_MEMORY_BOOTSTRAP_NODE_TYPES = frozenset((
    BuiltinNodeTypes.LLM,
    BuiltinNodeTypes.QUESTION_CLASSIFIER,
    BuiltinNodeTypes.PARAMETER_EXTRACTOR,
))
def get_node_creation_preload_selectors(*, node_type, node_data):
    if node_type not in _MEMORY_BOOTSTRAP_NODE_TYPES or getattr(node_data, "memory", None) is None:
        return ()
    return (system_variable_selector(SystemVariableKey.CONVERSATION_ID),)
```

**正确写法**（前端 `types.ts` 里的 `Memory` 类型）：

```json
"memory": {
  "role_prefix": { "user": "用户", "assistant": "助手" },
  "window": { "enabled": true, "size": 10 },
  "query_prompt_template": "{{#sys.query#}}"
}
```

**`context` 和 `memory` 的区别：**
- `context` = 把**外部检索结果**塞进提示词（RAG 用）
- `memory` = 把**历史对话**塞进提示词（多轮用）

## 坑 21：Dify 自带的 question-classifier 判定不稳，换成 LLM + if-else

**现象**：「书籍转技能这个 Skill 能干什么？」被分到「直接回答」，
**隔离测试下仍然误判**（排除了记忆污染）。

**排查过程：**

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① | 怀疑记忆污染 | 隔离测试（新 conversation_id）→ **仍然错** |
| ② | 读源码看提示词模板 | 发现是**英文 few-shot**（讲客户反馈分类），配中文类名 |
| ③ | 改类名：「直接回答」→「与知识库无关」 | **还是错** |
| ④ | **换成 LLM 输出 1/2 + if-else** | ✅ **5/5 全对** |

**为什么自带分类器不稳** —— 它的提示词模板
（`graphon/nodes/question_classifier/template_prompts.py`）里：

```
{"input_text": ["..."], "categories": [{category_id, category_name}], "classification_instructions": [...]}
```

- 例子全是英文的客户反馈分类
- 类名（`category_name`）对判定影响最大，`instructions` 只是辅助
- 类名语义不够「排他」时，模型容易被字面吸引（「能干什么」→ 觉得可以直接回答）

**换成 LLM + if-else 的好处：**
- 提示词完全可控，能写「拿不准就选 1，因为选错的代价不对称」
- 输出只有 1 或 2，用 if-else 判断 `contains "1"`，不依赖模型输出 JSON

**⭐ 通用结论**：框架自带的组件不一定比手写提示词准。
遇到判定不稳时，**先看清楚它内部用的什么提示词**，再决定是调参还是换掉。

# 十二、对话式入库（2026-10-07）

## 12.1 为什么加这个

**原来的形态**：员工要发视频进来，得有人登服务器敲命令行。**员工不会用命令行。**

**目标形态**：员工只面对一个对话框 ——

```
员工：帮我把这个视频的知识点提取出来放进知识库 https://...
系统：收到，已经开始处理这个视频了。
      视频链接：https://...
      任务编号：7535c3e7f250
      处理需要一点时间（几分钟内）。完成后你直接问视频里的内容就行。
（几分钟后）
员工：把 Agent 连上 ComfyUI 需要什么条件？
系统：需要三个条件：1. 一台带独立显卡的电脑 2. 安装好 ComfyUI
      3. 装一个支持 MCP 的 Agent 客户端（如 Claude、Codex、Cursor）
```

## 12.2 核心矛盾：入库要 15 秒到 2 分半，但对话不能干等

| 视频时长 | 全链路耗时 |
|---|---|
| 27 秒 | 15.1 秒 |
| 87 秒 | 31.6 秒 |
| 145 秒 | 61.1 秒 |
| **11 分 37 秒** | **147.2 秒** |

**而 Dify 的工作流是同步的，默认超时 60 秒 —— 长视频直接失败。**
**而且「先回复『收到』再后台跑、跑完再通知」这件事，同步工作流做不到。**

**→ 所以必须把入库拆出工作流，做成独立的常驻服务。**

## 12.3 架构：Dify 只负责「受理」，入库交给外部服务

```
员工发链接
   │
   ├─ 意图判断（LLM）→ 输出 3
   │
   ├─ 提取链接（代码节点，正则抓 URL）
   │
   ├─ HTTP 节点 → POST http://host.docker.internal:8090/ingest
   │                 ↓ 立即返回 202 + job_id（不等）
   │
   └─ 组装话术（代码节点）→ 回复「收到，任务编号 xxx」
                          │
                          ↓
        ┌─────────────────────────────────────┐
        │  入库服务（独立进程，端口 8090）      │
        │  POST /ingest   → 收链接，起后台线程  │
        │  GET  /jobs/<id> → 查状态            │
        │  GET  /health    → 健康检查          │
        │                                     │
        │  后台跑：下载 → 转写 → 纠错 → 入库    │
        └─────────────────────────────────────┘
```

**⭐ 关键设计：Dify 只做「受理 + 回执」，真正的重活在外面跑。员工 1 秒内收到回复，不用等。**

## 12.4 入库服务的实现

**文件**：`05-脚本与工具\ingest-service.py`（零依赖，Python 标准库 `http.server`）
**启动**：`05-脚本与工具\入库服务.ps1`（含 start / stop / status / restart）

**为什么用标准库而不是 FastAPI**：这台机器没装 FastAPI，而服务只有 4 个端点。
**为了 4 个端点去装一个框架、还会污染 DSH 的 Python 环境，不划算。**

**复用**：直接 `import` 现有的一键脚本，复用 `download_video` / `transcribe` /
`correct_transcript` / `write_to_dify` 四个函数，**没有重写任何链路逻辑**。

**端点：**

| 端点 | 作用 | 返回 |
|---|---|---|
| `GET /health` | 健康检查 | 逐项检查 Ollama / Dify / ffmpeg / node / 抓取服务 |
| `POST /ingest` | 提交链接 | `202` + `{job_id, status:"queued"}`，**立即返回** |
| `GET /jobs/<id>` | 查单个任务 | `{status, stage, progress, title, doc_id, logs}` |
| `GET /jobs` | 最近 20 个任务 | `{jobs: [...]}` |

**任务状态机：**
```
queued(排队中) → running(下载中 5% → 转写中 25% → 纠错中 60% → 入库中 80%)
                                              → done(100%) / failed
```

**⭐ 任务落盘**（`_ingest-jobs.json`），服务重启后历史还在。

## 12.5 意图从 2 类扩成 3 类

**改造前：** `1 = 查知识库`　`2 = 直接回答`

**改造后：** `3 = 链接入库`　`1 = 查知识库`　`2 = 直接回答`

**判定规则（提示词的要点）：**
- **带视频链接 → 一律算 3**（哪怕没明说要入库）
- 问「入库好了吗」→ 算 1（查库），后面会查状态
- 问助手自己 / 打招呼 / 与知识库无关 → 2

**if-else 的三分支配置**（Dify 支持多 case）：
```json
{
  "_targetBranches": [
    { "id": "case-ingest", "name": "链接入库" },
    { "id": "case-kb",     "name": "查知识库" },
    { "id": "false",       "name": "ELSE" }
  ],
  "cases": [
    { "case_id": "case-ingest",
      "conditions": [{"variable_selector": ["llm_intent","text"],
                      "comparison_operator": "contains", "value": "3"}] },
    { "case_id": "case-kb",
      "conditions": [{"variable_selector": ["llm_intent","text"],
                      "comparison_operator": "contains", "value": "1"}] }
  ]
}
```

**⭐ 顺序很重要：先判「入库」（更具体），再判「查库」。**

## 12.6 「库里没有」时引导发链接

**这是把「入库」和「查询」两条路自然连起来的关键。**

**改造前：**
```
知识库里没有关于「xxx」的内容。          ← 说完就结束，用户不知道下一步
```

**改造后：**
```
知识库里没有关于「xxx」的内容。

如果你手上有讲这件事的视频，把链接发给我，我帮你存进知识库，之后就能直接问了。
```

**⭐ 这一句把闭环补上了：查不到 → 引导入库 → 入库后就能查到。**

## 12.7 端到端实测

```
第 1 步：员工发链接
  「帮我把这个视频的知识点提取出来放进知识库 https://b23.tv/HHucesn」

# 十三、坑 22：Dify 的 SSRF 保护挡住内网调用

## 症状

HTTP 节点调用 `http://host.docker.internal:8090/ingest` 失败：

```
Access to 'http://host.docker.internal:8090/ingest' was blocked by SSRF protection
(e.g. SSRF_PROXY_ALLOW_PRIVATE_IPS=172.21.0.0/16 to allow 172.21.0.0/16).
The URL resolves to a private, loopback, link-local, or otherwise
non-public network address.
```

## 排查过程（中间走了一次弯路）

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① | 从容器 `curl 172.19.0.1:8090/health`（**网关 IP**）| ❌ 超时 |
| ② | 换成 `host.docker.internal:8090/health` | ✅ **200，服务完全正常** |
| ③ | 走 SSRF 代理（`-x http://ssrf_proxy:3128`）| ❌ Squid 拒绝 |

**⭐ 弯路在哪**：第一步用了**网关 IP**（`172.19.0.1`），超时后一度以为
「容器根本连不到宿主机」。**实际上 `host.docker.internal` 是通的，
唯一障碍就是 SSRF 代理。**

**教训：测连通性要用正确的地址。Docker Desktop for Windows 上，
宿主机是 `host.docker.internal`（解析到 `192.168.65.254`），不是网段网关。**

## 根因

Dify 有个 Squid 代理（`ssrf_proxy` 容器）拦截所有出站请求，
防止 LLM / HTTP 节点被诱导去访问内网。

```
SSRF_PROXY_ALLOW_PRIVATE_IPS = 172.19.0.250/32    ← 默认只放行一个 IP（沙箱）
host.docker.internal → 192.168.65.254              ← 不在白名单 → 被拦
```

**⭐ 注意还有一层**：`host.docker.internal` 在容器里同时有 IPv6 记录
（`fdc4:f303:9324::254`），但 `getent ahosts` 优先返回 IPv4（`192.168.65.254`）
—— **白名单要填 IPv4 那个。**

## 解法

**改 `D:\Dify\dify-main\docker\.env`：**
```ini
# 改前
SSRF_PROXY_ALLOW_PRIVATE_IPS=172.19.0.250/32
# 改后
SSRF_PROXY_ALLOW_PRIVATE_IPS=172.19.0.250/32,192.168.65.254/32
```

**然后重启两个容器**（proxy 改了配置，api 可能缓存了环境变量）：
```powershell
cd D:\Dify\dify-main\docker
docker compose up -d ssrf_proxy
docker compose up -d api
```

**⭐ 安全提醒**：这一步等于**允许 Dify 的工作流访问宿主机**。
对自托管、自己用的场景没问题；**如果 Dify 要开放给外部用户用，
要慎重评估** —— 因为 LLM 或 HTTP 节点理论上可以被诱导去访问内网其他服务。

**改动已备份**：`D:\Dify\dify-main\docker\.env.bak-20261007-162004`

## 验证

```powershell
# 容器里直连（不走代理）
docker exec docker-api-1 curl -s http://host.docker.internal:8090/health
# → {"ok": true, "checks": {...}}

# 白名单是否生效
docker exec docker-ssrf_proxy-1 env | grep ALLOW
# → SSRF_PROXY_ALLOW_PRIVATE_IPS=172.19.0.250/32,192.168.65.254/32
```

# 十五、合规改造：只存「知识点」，再从校对稿摘回「事实」（2026-10-07）

## 15.1 为什么要改

**原来的做法**：把纠错工作流的三节（`## 校对稿` / `## 知识点` / `## 问答对`）
**全部**写进知识库。

**问题**：「校对稿」是**他人视频的完整原文**。

**⭐ 著作权法的「思想 / 表达二分法」：**

| | 受保护 | 例子 |
|---|---|---|
| **思想** | ❌ **不受保护** | 「先讲痛点再给方案」的结构；「三线性差值省显存」这个知识点 |
| **表达** | ✅ 受保护 | 他具体说的那段话、那个文案、那个画面 |

**⭐ 存完整转写稿 = 复制「表达」→ 风险最高的一档。**

**⚠️ 「只给一家公司内部用」不构成豁免** —— 使用主体是商业实体、目的是经营活动、
用了他人的作品，三个条件都满足，就属于商业使用。

## 15.2 改造方案：三段式

```
纠错工作流输出
  ├─ ## 校对稿   →  ❌ 丢弃（表达，风险最高）
  │                   ↓ 但从中摘回含数值/参数的句子
  ├─ ## 知识点   →  ✅ 保留（思想，风险低）
  └─ ## 问答对   →  ✅ 保留（提炼产物，且问答形式对检索更友好）
```

**⭐ 「事实摘录」为什么可以留：**

**著作权法保护「表达」，不保护「事实」。** 数值、型号、参数名、版本号是事实，不受保护；
**而它们恰恰是检索时最有用的信息**（用户常问「显存多少」「几步」「哪个版本」）。

**⭐ 三条限制（防止变相保留全文）：**

| # | 限制 | 实现 |
|---|---|---|
| ① | 只摘含数值或已知参数名的句子，纯观点句不摘 | `FACT_PATTERNS` 正则 |
| ② | 总长封顶 | `FACT_MAX_CHARS = 700` |
| ③ | 明确标注「原文摘录」，不冒充自己的话 | 段落标题写死 |

## 15.3 代码实现

**文件**：`05-脚本与工具\one-click-pipeline.py`

**新增常量：**
```python
FACT_MAX_CHARS = 700

FACT_PATTERNS = [
    r"\d+(?:\.\d+)?\s*(?:G|GB|MB|T|K|k|万|亿|秒|分钟|小时|帧|步|张|个|次|倍|%|％|字|条|段|部|层)",
    r"[Vv]\d+(?:\.\d+)?",
    r"\d+(?:\.\d+)?\s*(?:top_?k|temperature|cfg|steps?|denoise|seed|batch)",
    r"FP16|FP8|BF16|三线性|双线性|罗尔|LoRA|WCA8|底膜|采样器|调色台|柔雾|泛光|暖晕",
    r"ComfyUI|MiniMax|H3|Claude|Codex|Cursor|MCP|SKILL|Skill",
]
```

**新增函数 `extract_facts(corrected, max_chars)`：**
1. 定位 `## 校对稿` 那一节
2. 按中文句号/问号/感叹号/分号/换行拆句
3. 只留命中 `FACT_PATTERNS` 且长度 6–200 字的句子
4. 去重（按前 24 字）+ 按长度封顶
5. 包成 `## 关键参数（原文摘录）` 段

**`build_chunks` 接入：**
```python
if "校对稿" not in keep_sections:
    facts, n_facts = extract_facts(corrected)
    if facts:
        chunks.append(prefix + facts)
        log(f"  ⭐ 从校对稿摘回 {n_facts} 句关键参数（{len(facts)} 字）")
```

**可回退：** 环境变量 `KEEP_SECTIONS=校对稿,知识点,问答对` 可恢复原行为。

## 15.4 重入库

**文件**：`05-脚本与工具\reingest-compliance.py`

**⭐ 用本地已下载的视频重跑，不重新下载**（避开链接失效，也省时间）：

```powershell

python reingest-compliance.py --go       # 真正执行
python reingest-compliance.py --go --only MiniMax   # 只跑一个
```

**流程**：从文件名反解 `info` → `transcribe` → `correct_transcript` → `build_chunks` → `write_to_dify`

# 十六、坑 23：主题判断的判断依据必须来自知识库实际内容

## 症状

合规改造后跑验证，6 题里 4 题**主题判断全错**：

```
❌「新版三彩工作流和上一版的区别？」→ AI工具（应 AI视频）→ 拒答
❌「三彩工作流是什么？」           → AI工具（应 AI视频）→ 拒答
❌「MiniMax H3 怎么用？」          → AI工具（应 AI视频）→ 拒答
```

**⭐ 但「MiniMax H3 小显存为什么用三线性差值？」是对的。**

## 根因

**原来的主题判断提示词是我凭想象写的：**
```
· AI工具 —— Agent、ComfyUI、MCP、工作流搭建、本地部署这类
· AI视频 —— 视频生成、显存、模型量化、LoRA、生成参数这类
```

**⭐ 问题：提示词跟知识库实际内容对不上号。**

- 「三彩工作流」—— 提示词里只有泛泛的「工作流搭建」，LLM 看到「工作流」就归到 AI工具
- 「MiniMax H3」—— 含专有名词，LLM 能对上「视频生成」
- 「三彩」—— 提示词里没有，LLM 无从判断

## 解法：把知识库真实内容写进提示词

**脚本**：`dify-mcp\_fix-topic-prompt.mjs`

**做法**：从知识库读出每个文档的「知识点」条目，自动生成分类描述：
```
【AI视频】《新人6G显存跑MiniMax H3！一键直出4分钟成片》
   · 新版三彩工作流推翻了旧版一彩、二彩部分
   · 一彩使用质量较高的底膜以保证视频基底质量
   · 大显存显卡可使用FP16模型（约占用3G显存）
   · 工程中的「添加分段」功能支持多段输出：每段可设置不同提示词和参考图

【AI工具】《把 Agent 连上本地 ComfyUI！：让 Agent 帮你把 ComfyUI 自动玩明白》
   · ComfyUI MCP 本地版正式发布
   · 支持用自然语言构建、编辑和运行工作流
   ...
```

**⭐ 并加了关键判据：**
```
· 问「工作流怎么搭」「提示词怎么写」「某个工具怎么用」时，
  要看这个工具/工作流属于哪一类 —— 不要因为出现「工作流」三个字就都归到工具类。
· 如果问题提到具体的视频名、UP 主名、或上面列出的关键词，直接归到那条内容所属的类别。
```

**结果：主题判断 0/4 → 3/4。**（第四题的问题在意图判断，见坑 24）

**⚠️ 副作用**：新增视频时要重新跑一次这个脚本，否则提示词不知道新内容。

# 十七、坑 24：意图判断会把「有实质内容的问题」误判成闲聊

## 症状

修完主题判断后，还剩一题失败：
```
「视频生成的时间为什么变长了？」
→ 意图判断 = "2"（直接回答）→ 根本没走到检索
```

## 根因

**原来的意图判断提示词：**
```
【输出 1 = 要查知识库】
· 问「XX 能干什么」「XX 是什么意思」「怎么设置」「需要什么条件」
· 用「那个视频」「上次说的」指代视频内容

【输出 2 = 直接回答就行】
· 打招呼、道谢
· 问助手自己
· 与知识库完全无关
```

**⭐ 「视频生成的时间为什么变长了？」—— 是个「为什么」类问题，**
**不含「怎么设置」「需要什么条件」这类显式信号，LLM 就判成了 2。**

## 解法：加显式规则

**脚本**：`dify-mcp\_fix-intent-prompt.mjs`

**加了两段：**
```
· 问某个工具/技术/功能是什么、怎么用、为什么、有什么区别
  例：三彩工作流是什么、MiniMax H3 怎么用、显存不够怎么办、
      视频生成的时间为什么变长了、新版和上一版差在哪

⚠️ 关键：「为什么」「怎么办」「有什么区别」这类有实质内容的问题，
   哪怕你不知道知识库里有没有，也一律输出 1 —— 让检索去判断有没有，
   不要在这里替它决定。只有下面那几种才算 2。
```

**结果：意图判断 8/8 正确。**

# 十八、坑 25：LLM 提取知识点会失真 —— 但这次不是它的错

## 症状

改造后有道题一直拒答：
```
「视频生成的时间为什么变长了？」
→ 检索到 4 条，但 LLM 判「知识库里没有」
```

**⭐ 而且知识库里写着自相矛盾的内容：**
```
- 新版工作流...但一彩生成时间稍长（新版两分十三秒 vs 旧版两分十五秒，768分辨率）。
```

**133 秒 < 135 秒 —— 数据说新版更短，结论却说「稍长」。**

## 排查

**⭐ 第一反应是「LLM 编造了数值」。但去原始转写稿里核对：**

```powershell
# 在转写稿里搜关键数字
「两分」出现 2 次   ✅
「13秒」出现 1 次   ✅
「15秒」出现 1 次   ✅
「768」出现 1 次    ✅
```

**原文（转写稿）里的原话：**
```
但是它稍微有一点问题的是生成的时间要长一些
我们看一下这个两分13秒 那原来的用时是两分15秒
...这个是768 所以新版的可能用时时间更久一点（一彩）
但是二彩和三彩由于进行了极大的改善 它生成的时长会比上一版的要短很多
```

## 结论：**LLM 一个数字都没编，是视频作者自己说错了**

| 原文说 | 数学上 |
|---|---|
| 新版 **两分13秒** vs 旧版 **两分15秒** | 133 秒 < 135 秒，**新版更短** |
| 但结论是「新版的可能用时**更久**一点」| ❌ **矛盾** |

**⭐⭐ 所以那次「拒答」是正确行为** —— 知识库忠实反映了矛盾信息，
LLM 无法给出确定答案就拒答，**而不是瞎编一个**。

**⭐ 这其实是个好结果：说明系统遇到矛盾信息时会拒答，不会编造。**

## ⭐ 这一条的方法论价值

**遇到「模型答错了」，先分清是三种情况中的哪一种：**

| 情况 | 表现 | 怎么办 |
|---|---|---|
| **输入素材本身有问题** | 本例 —— 作者口误 | **不用改**，拒答是对的 |
| **模型提取失真** | 提取结果跟原文不符 | 改提取提示词 |
| **检索/路由错** | 提取没问题但没命中 | 改检索或路由 |

**⭐ 如果不做这一步核对，很容易把「素材问题」误判成「模型问题」，然后去改一个本来没错的地方。**

## ⭐ 坑 26：裸调 `apiCall` 不会自动刷新 token

**解法**：

import { refreshConsoleCookies, storeCookies } from "./src/core/auth.ts";

const rf = await refreshConsoleCookies(BASE, cookies);

```

**⭐ `refreshConsoleCookies` 打的是 `POST /console/api/refresh-token`，

**⭐ 还有几个 API 路径值得记：**

# 2026-10-08 深夜新增：长视频与质量保障（坑 27–33）

> 本轮从「64 分钟视频入库只剩 105 字」这一个事故出发，补出了整套质量保障层。
> 完整设计见 [`质量保障层.md`](质量保障层.md)。

## ⭐ 坑 27：长视频静默丢数据 —— 流程报「成功」，内容却没了

**症状**：64 分钟视频入库后，知识库里只有 **105 个字**，而日志一路打印「✅ 完成」。

**根因**：纠错 LLM 的输出 `finish_reason = "length"` —— 被 `max_tokens` 截断了。
截断位置恰好让 `## 知识点` / `## 问答对` 两节没生成，而合规策略正确地丢弃了 `## 校对稿`
→ **主体内容全丢，且没有任何一处报错**。

**解法**（三步）：
1. 纠错节点显式设 `max_tokens = 8000` + `thinking = false`
2. 改成**分块 map-reduce**：按 3500 字 / 句子边界切块，逐块纠错再合并去重
   （`''.join(分块) == 清洗后原文` 校验切分无损）
3. 加**校验闸门**：每块必须有含实际条目的知识点与问答对，否则**拒绝入库**

**效果**：同一个视频 —— **105 字 → 9178 字 / 12 段**。

**⭐ 教训**：一个能报「完成」的坏产出，比一个报错的失败危险得多。
判据必须从「有没有这个标题」升级为「**标题下有没有实质内容**」——
这就是「真检查」与「存在性检查」的区别。

## ⭐ 坑 28：内容超过约 8000 字就入不了库（命令行长度上限）

**症状**：`FileNotFoundError: [WinError 206] 文件名或扩展名太长`

**根因**：`write_to_dify()` 把上传 payload 当**命令行参数**传，内容一大 base64 就爆
Windows 的 32767 字符上限：

| 内容 | UTF-8 | base64 | 结果 |
|---|---|---|---|
| 3091 字 | ≈9KB | ≈12K | ✅ 通过 |
| 9178 字 | ≈27KB | **≈36.7K** | ❌ WinError 206 |

**⚠️ 实测 CLI 的 `--file` 不支持 `@file`，也不支持 `-`（stdin）**，只认内联 JSON —— 两条常规绕法都不通。

**解法**：新增桥接 `_upload-file.mjs`，从**文件**读 payload，
直接调 `POST /console/api/files/upload`（multipart）。实测 33,140 字符的 base64 上传成功。

## ⭐ 坑 29：模块在一个进程里只能 import 一次

**症状**：多个测试模块一起跑（各自用 importlib 载入同一个 pipeline 模块）时报
`ValueError: I/O operation on closed file`。

**根因**：pipeline 在 import 时**无条件**执行
`sys.stdout = io.TextIOWrapper(sys.stdout.buffer, ...)`；
第二次 import 时 `sys.stdout.buffer` 已是被包过的，底层 buffer 已关闭。

**解法**：加幂等守卫 —— 在 `sys` 上放标志位，判断是否已经包过。

## ⭐ 坑 30：LLM「纠错」把正确的专名改错了（外加检查器自己的两个 bug）

**症状**：转写稿里正确的 `Reason加Act`，被 LLM 纠错改成 `Reason加Actor`，然后写进了知识库。

**解法**：设计**专名漂移检查** —— 从原始转写稿抽候选专名，纠错后逐个核对（按词边界），
不在就用相似度猜改写结果并告警。

**写这个检查器时自己踩的两个坑**（都值得记）：
1. **子串匹配太松**：用 `"Act" in "Actor"` 判断「专名还在不在」
   → `Act` 是 `Actor` 的子串，**最该抓的改写被漏报**。必须加字母/数字词边界。
2. **猜测误报**：`ReAct` 与 `Actor` 对 `Act` 的相似度都是 0.75，
   不筛「原稿里没有的新词」就会误报成 `Act → ReAct`。

**⭐ 诚实说明**：这是**降级方案**。理想解是「**专名以画面 OCR 为准**」——
声学模型解决不了同音词（如「短距」/「短剧」），画面文字才是可靠来源。本机未接 OCR。

## ⭐ 坑 31：库变大 → 主题提示词膨胀 → 分类退化

**症状**：库从 8 篇涨到 26 篇后，问「调色台的操作流程」被判成 `AI工具`（应为 `AI视频`）
→ 该主题文档被元数据过滤挡掉 → **拒答**。

**根因**：主题判断的提示词里塞了**全库**的视频标题 + 知识点 →
库一变大，提示词从 **2079 字爆到 6335 字**，分类精度反而下降。

**解法**：提示词改成**紧凑版** —— 每类只留有限个高辨识度关键词 + 显式消歧规则，
**大小与库规模脱钩** → **6335 字降到 744 字**（每问省约 2800 token），判断恢复正确。

**⭐ 教训**：把一个**会随数据规模增长**的东西塞进提示词，短期能跑、**长期必坏**。
提示词的复杂度应该与**业务复杂度**挂钩，不该与**数据量**挂钩。

## ⭐ 坑 32：B站多分P 只入库了 P1

**症状**：19 分P 的课程（总 124.5 分钟）入库后，只有第 1 讲进了库，其余 18 讲**静默丢失**。

**根因**：`fetch_one_video` 返回的**顶层 `cid` 是 P1 的**；只拿它取播放地址，自然只取到 P1。
分P 信息在 `d["pages"]` 里。

**解法**：读 `pages[]` 逐P 下载、各自成文；文件名与文档名都带 P 号（否则互相覆盖 / 混淆）。

**⭐ 教训**：一个 API 的「顶层字段」往往只代表列表的第一项。
看到列表型资源，先找 `pages` / `items` / `list`。

## ⭐ 坑 33：同一节课的重复投稿会被入库两次

**症状**：19 分P 课程里 P2 与 P3 标题一样、时长一样，两份都进了库，检索时互相抢位。

**怎么确认是重复的**（不是靠标题猜）：

| 对比项 | P2 | P3 |
|---|---|---|
| **全量音频 MD5** | `D6CB799B29CE…` | **完全相同** |
| 精确时长 | 362.927891 秒 | 362.927891 秒 |
| 视频文件 | 8.9 MB | 9.2 MB（**重编码过，所以不同**）|

→ 音频逐字节相同 = 同一份录音；视频不同只因重新编码。

**解法**：下载后先算**音频前 120 秒的 md5**，命中台账就跳过（连转写都不做）。
**按内容去重，而不是按链接去重**。

**⭐ 分辨力验证**（防「把不同课当重复丢掉」）：同一文件两次指纹必须相同，
且**不同音频必须算出不同指纹** —— 这条比上一条更重要。

## 📌 技术事实（不是坑，但选型时会用到）：文档名不参与检索

**结论**：改文档名**不会**改变检索结果。参与检索的「名字」是**分段正文开头的 `【标题】` 前缀**。

**三条证据**：
1. **嵌入只吃正文** —— `api/core/rag/datasource/vdb/vector_factory.py:182/240`：
   `self._embeddings.embed_documents([document.page_content for document in documents])`
2. **建分段的 metadata 里没有 name** —— `index_processor/processor/paragraph_index_processor.py:200`
3. **Qdrant payload 实测**：`metadata` 里只有 `dataset_id / doc_hash / doc_id / document_id / source`，
   而 `source` 是上传时的**临时路径**，也不是文档名

**推论**：
- 「按内容命名文档」对检索**零收益**
- 想改善**跨视频区分度**，要改的是**分段前缀**（`build_chunks` 里的 `prefix`），不是文档名
- 反过来，文档名是**给人看的**；若将来重新打开「标注来源」，名字越接近视频原标题越有用
